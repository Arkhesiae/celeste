# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Celeste is a shift-management / planning app (teams, rotations, shift substitutions between users, tickets, announcements) for "centers". Two parts, deployed together:

- `backend/` — Node 20, Express 5, Mongoose 9 (MongoDB), ES modules (`"type": "module"`). Code comments, logs and user-facing messages are largely in French.
- `front/` — Vue 3 (Composition API, `<script setup>`), Vuetify 4, Pinia stores, Vite, Capacitor (Android/iOS wrapper).

Cursor rule (`.cursor/rules`): always provide solutions that consider the full front-to-back workflow, and always use the Vue Composition API with `<script setup>`.

## Commands

Backend (`cd backend`):
- `npm run dev` — nodemon `server.js`; `npm start` — plain node
- `npm run format` — prettier on `src/**`
- `npm test` runs `node --test`: `test/compatibility.rules.test.js` (pure rest / workload rules against an independent oracle; tests marked `todo` describe known defects, see `docs/quality/blocking-issues.md` #45, #47) and `test/compatibility.db.test.js` (`getCompatibleSwitches` on a scratch database `TEST_MONGO_URI`, default `mongodb://127.0.0.1:27017/celeste_test_compat`, dropped before and after, skipped when MongoDB is unreachable). No other test suite exists.

Front (`cd front`):
- `npm run dev` (or `npm run front` for `--host`), `npm run build`, `npm run lint` (eslint --fix)
- Capacitor: `npm run cap:sync`, `cap:open:android`, `cap:open:ios`

Local setup (see CONTRIBUTING.md, marked incomplete): create `front/.env.local` (`VITE_API_URL=http://localhost:3000/api`, `VITE_NODE_ENV`, `VITE_ADMIN_MAIL`, `VITE_ADMIN_PASS`) and copy `backend/.env.example` to `backend/.env` (the only file the backend loads, via `import 'dotenv/config'`; `.env.development` is not read): every variable the code reads is listed there with its default and whether it is required (`MONGO_URI`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `FRONT_URL`, `FRONTEND_URL`, `PORT`, `LOCAL_ADMIN_PASSWORD`, `SES_*`, ...). Needs a local MongoDB **replica set** (`docker compose -f backend/docker-compose.dev.yml up -d`). Mails are printed to the console unless `NODE_ENV=production` (`MAIL_SERVICE` is read but has no effect). Optional: `GEOCODER_URL` (default `https://nominatim.openstreetmap.org/search`) and `GEOCODER_USER_AGENT` (default `Celeste-app/1.0`) for the center map geocoding (see Center routes below); `EXPLORE_VARIATIONS=true` turns on the exploration of ambiguous shift variations in demand lists (off by default, see `docs/architecture/demand-categorization.md`).

Deploy: root `Dockerfile` builds `front` and copies `dist` into `backend/public`, so one Express container serves both API and SPA. `docker-compose.yml` adds mongo, nginx, certbot, a backup job (`scripts/backup_mongo.sh`) on an external `celeste` network, using `.env.prod`.

## Backend architecture

Layering: `routes/` → `controllers/` → `services/` → `models/` (+ `utils/` for pure helpers, `bootstrap/` for the admin seed run at startup, `dev/` for development fixtures called by the dev-only `/api/dev` routes). Pure helpers live in `utils/`: `dates/` (Temporal day helpers, see Dates below), `ids.js` (`sameId`, `idOf`, `isValidId` — never compare ids with `===` or `.toString() ===`), `names.js` (`fullName`, `shortName`), `mongo.js` (`inTransaction(fn, { session })`, `findOrThrow(Model, id, { message, select, populate, session })`), `math.js` (`mod`), `shifts/` (shift hours, night control). Domain computations that read the database live in `services/planning/` (`computeUserShifts`, `computeShiftOfTeam`, `generateShiftsMap`), `services/rotation/rotation.latest.js` (`findLatestRotation`), `services/team/` (`team.cycleIndex.js`, `team.segments.js`, `team.atDay.js`: cycle formula, team occurrences, owner team of a day) and `services/substitution/` (`compatibility/compatibility.rules.js`, `compatibility/compatibility.categorize.js`, `compatibility/compatibility.variations.js`, `substitution.userPool.js`); `services/center/center.timezone.js` gives a center's time zone. Use these helpers instead of writing new local copies.

- Configuration: environment variables are read where they are used (`process.env.X`), and the `.env` file is loaded once by `import 'dotenv/config'`, the first import of `server.js` (so the other modules see it). `backend/config/` holds the **constants** (policy numbers, durations, limits) shared by the backend, one file per topic, each value documented: `points.js` (`MIN_POINTS_BALANCE`, `MAX_POINTS_TO_ACCEPT_REQUEST`, `SHIFT_POINTS_PER_HOUR`, `SHIFT_BASE_POINTS`), `auth.js` (`DEFAULT_ACCESS_TOKEN_EXPIRY`, `REFRESH_TOKEN_DAYS` / `REFRESH_TOKEN_EXPIRY` / `REFRESH_TOKEN_MAX_AGE_MS`, `OTP_VALIDITY_MS`), `limits.js` (body and avatar sizes, maximum periods of the date-range endpoints), `schedules.js` (cron expressions, `DEFAULT_REMINDER_HOUR`), `server.js` (`DEFAULT_PORT`, MongoDB connection retries), `paths.js` (`PUBLIC_DIRECTORY`, `AVATARS_DIRECTORY`), `workRules.js` (legal rest and workload thresholds of the compatibility computation), `compatibility.js` (planning radius, variation exploration bounds), `geocoding.js` (geocoder pause, timeout, retry delay). Put a new shared constant there instead of redefining it in a file; a value that only one file uses and that is not a policy number stays local. Avatars uploaded by users live in `backend/public/avatars/`, which is **not tracked by git** (created at startup, keep it in a volume in production).
- `server.js`: CORS (explicit origin allowlist incl. `capacitor://` origins), mounts `routes/index.js` under `/api`, serves `public/` (the built SPA, with catch-all for non-`/api` paths) and `/api/avatars`, then `errorHandler` last. On Mongo connect (5 retries) it runs `initializeRules()`, `createAdmin()`, `createLocalAdmin()` before listening.
- Errors: **never answer an error with `res.status(4xx/5xx).json(...)`** and never build a custom error shape. Validate and `throw new AppError(message, status, code?)` (`error/AppError.js`); in a `try/catch` just call `next(error)` (handlers take `(req, res, next)`; in a promise chain use `.catch(next)`). `middleware/errorHandler.js` is the single place that decides what the client sees, as `{ error, message, code }` (both `error` and `message` are set because the front reads either): an `AppError` is returned as is; framework 4xx errors (invalid JSON, payload too large) and `MulterError` (400) pass through; **anything else becomes a generic 500 (`Erreur interne du serveur`)** and is only logged, so raw Mongoose/driver text never reaches clients. Consequently, an error whose message the user must see has to be an `AppError` with its status in the service/util that detects it (a plain `Error` with a `.status` property is *not* honoured), and controllers must not match on `error.message`. Do not use 409 for plain errors: the front `apiFetch` treats a 409 as an approval request (`needsApproval`) and does not throw. Auth uses `middleware/authMiddleware.js` (Bearer JWT → `req.user`; `isAdmin` etc.). Auth flows (login, refresh token, password reset, OTP, account recovery) live in `services/auth/`.
- Center routes (`routes/center.routes.js`): only `GET /center` is public (sign-up, account recovery and contact forms need the list before an account exists) and it returns just `_id, name, OACI, type, zone, timeZone` (`timeZone` is public on purpose: the activation date picker needs it to grey out past days); everything else requires a token — create/update/delete and the cross-center reads (`/admins`, `/users/count`, `/all-active-rotations`) are master-admin only, `/:id/active-rotation` is limited to members of that center (`authorizeCenterParam`).
- Centers map (dashboard): `GET /center/map` (any logged-in user, `services/center/center.map.js`) returns, for every non-deleted center that has a position, `{ _id, name, OACI, type, latitude, longitude, open, accepted, isOwn }` where `open` / `accepted` count the center's upcoming demands (day of the original shift today or later in that center's time zone) and `pendingLocations` counts centers still without a position. It is cross-center on purpose and returns counts only (no demand content, no person). Positions are found **from the center name** by `services/center/center.geocode.js` (Nominatim, tries `<name>` then `aéroport <name>`, one lookup per second as the usage policy asks, a descriptive User-Agent), stored once in `Center.location` (`latitude`, `longitude`, `displayName`, `geocodedAt`), and a name that finds nothing is remembered in `Center.locationLookupFailedAt` and retried after 7 days. Lookups run in the background from the map request (`ensureCenterLocations`, never awaited, one at a time), so a first call may return fewer centers; renaming a center (`PUT /center/:id`) clears its position. The public `GET /center` does not expose the position. Front: `components/Dashboard/CentersMapCard.vue` (Leaflet loaded on demand, about 43 kB gzip in its own chunk). **No tile service** (those need keys or can disappear): the background is a local GeoJSON of country outlines, `src/assets/map/countries.json` (Natural Earth, public domain; precise in Europe, coarse elsewhere; about 98 kB gzip, lazy), generated by `npm run map:build` (`scripts/buildMapData.mjs`, from the dev dependencies `world-atlas` and `topojson-client`) and drawn as SVG by Leaflet; sea, land and pins are colored through `--v-theme-*` CSS classes (`cm-*`), so they follow the Material 3 theme, light or dark (primary = open demands, secondary = only taken, surfaceVariant = none, a ring on the user's own center).
- Access control: a route is **public only if a screen needs it before login** (sign-up, login, contact form, landing): `GET /center`, `GET /team/public/:centerId`, `GET /user/info/:email`, `POST /user/create|check-email`, `POST /otp/*`, `POST /ticket/create`, `GET /stat*`, plus auth and the dev-only `GET /user/devlist` (404 in production); each returns the strict minimum. Everything else needs `verifyToken` **and a center guard** from `middleware/centerAuth.js` (master admin everywhere, everyone else only inside their own center, fail-closed): `authorizeCenterParam('centerId')` for a center in the URL — **the target center always goes in the URL (`/center/:centerId/...`), never in the body**, so the access rule is readable from the route and a spoofed body field changes nothing (creations are `POST /rotation/center/:centerId`, `POST /team/center/:centerId`, `POST /announcement/center/:centerId/send`; the global announcement `POST /announcement/send` is master-only), `authorizeResourceCenter(Model, { centerField, masterOnlyField })` or its instances `authorizeDemandAccess` / `authorizeTeamAccess` / `authorizeTicketAccess` / `authorizeRotationAccess` / `authorizeAnnouncementAccess` for a resource by id (`masterOnlyField` makes a flagged resource master-only, e.g. `isGlobal` announcements), `authorizeBodyResourcesCenter` for id lists, for users `authorizeTargetUserCenter` (self or colleague) and `authorizeSelfOrCenterAdmin` (self or the center's admin; put `isAdmin` in front for admin-only routes), and `resolveCenterId` for list routes that only need the caller's center in `req.user.centerId`. The caller's role and center are read from the JWT access token in one place (`loadCaller`; `centerId` is put in the token at login and refresh by `generateAccessToken`, so a change of center or role applies at the next token refresh, 15m by default, and a deleted user is not rejected by the guards until the token expires), and error texts are generic on purpose (no per-entity wording). `isAdmin` alone is **not** enough to act on a resource. The old `isUserOrAdmin` / `checkUserCenter` were removed (any admin could act on any user; the latter failed open).
- Serialization: `models/User.js` strips `password`, `refreshTokens`, `resetPasswordToken` and `resetPasswordExpires` from `toObject()`/`toJSON()`, so no endpoint can leak them by returning a user; they stay readable on the document for the auth flows. Never rely on a controller to remember to delete them.
- Rotation mutations (`routes/rotation.routes.js`) are guarded by `authorizeRotationAccess` (in `middleware/centerAuth.js`; creation uses `authorizeCenterParam`): a local admin can only touch rotations of their own center (master admin: all; fail-closed when the center is missing). A center cannot have two activations on the same date (adding one answers 400 `ROTATION_ACTIVATION_DATE_TAKEN`), and a new activation must be today or later in the center's time zone (400 `ROTATION_ACTIVATION_DATE_PAST`). Activation dates only change through `POST /rotation/:id/activate` and `POST /rotation/:id/remove-date` (one endpoint each: without `confirmed: true` in the body they only preview and answer 409 `{ needsApproval, changes }` when requests are affected; with a boolean `confirmed: true` they apply — the front calls `rotationService.setActiveRotation(id, date, confirm)` / `removeActivationDate(id, date, confirm)`, and the store takes `{ confirm }`), which cancels or converts the affected substitutions inside one transaction; `PUT /rotation/:id/update` only renames, and `PUT /rotation/:id/day` is refused (400 `ROTATION_HAS_ACTIVATIONS`) once the rotation has any activation date.
- Cron: `jobs/` (imported by `server.js`) uses node-cron; `requestJob` every 30 min cancels past substitution demands and completes/archives finished ones via `services/substitution/request.expiry.js`; `transactionJob` runs scheduled transactions (`services/transaction/`). `reminderJob` (hourly) sends the accepter of a replacement/switch a reminder the evening before (`services/substitution/request.reminder.js` → `sendReplacementReminderEmail`): "tomorrow" and the send hour are evaluated in each center's `timeZone`, from `REMINDER_HOUR` (default 18) local time; `Substitution.reminderSentAt` is claimed atomically before sending (released if the send fails) and reset to `null` whenever a request is accepted, so each accepter is reminded once. The accepter's email preferences (`all` and the `replacement`/`switch` category) are respected.
- Naming: route files `<resource>.routes.js` and controllers `<resource>.controller.js` are both singular and camelCase like the models and service folders (`calendarEntry.routes.js`, `accountRecovery.controller.js`, `services/calendarEntry/`; kebab-case is for URLs only, `/calendar-entry`), and `models/` and `services/` use the same singular word; **URL mounts are singular too** (`/api/user`, `/team`, `/rotation`, `/rule`, `/message`, `/ticket`, `/announcement`, `/public-announcement`, `/stat`, `/calendar-entry`, `/center`, `/substitution`; some sub-paths still name a plural, e.g. `/center/users/count`, `/stat/users`, `/user/teams/:centerId`), set in `routes/index.js` and called by `front/src/services/*Service.js`; **exports are named** in controllers, services and utils (group them with `import * as x from`; `export default` only for models and routers); **each `services/<domain>/` has an `index.js`** (`export *` of its files) that code outside `services/` (controllers, jobs, `server.js`, scripts, dev) imports, while files inside `services/` import the target file directly (a barrel between services creates import cycles), so a new service file is added to its domain's `index.js` and an exported name must stay unique inside the domain; **import style**: a controller imports each service domain once, as a namespace (`import * as rotationService from '../services/rotation/index.js'`, called `rotationService.createRotation(...)`, alias `<domain>Service`), after its other imports in the order libraries, `config`, `models`, `utils`, `error`, `services`, other controllers; a route file puts all its imports (libraries, `config`, `middleware` by name, `models`, then the controller as `import * as <resource>Controller`) above `const router = express.Router();` and registers handlers as `<resource>Controller.handler`; service files are `<domain>.<action>.js` (`rotation.create.js`, `request.accept.js`, and also the mails `email.otp.js` / `demand.emails.js` and the planning computations `planning.userShifts.js`, `planning.teamShift.js`, `planning.shiftsMap.js`; `<domain>.service.js` is accepted for a small domain with a single file: `publicAnnouncement`, `rule`, to be split by action when it grows). Controllers read **and validate** the request (shared checks in `utils/validation.js`: `assertId`, `assertEmail`, `assertDay`, `assertPositiveInteger`, `assertObject`, each throwing a 400 `AppError`; business rules stay in the services), call a service in `services/<domain>/` and answer, with one response shape: a read (GET) returns the resource itself without envelope, a write returns `{ message }` plus the resource the client needs (`user`, `preferences`, `changes`...), a change that needs approval returns 409 `{ needsApproval, ... }`; controllers do not log errors (`errorHandler` does) and do not rewrap service errors (done for `rotation`: `services/rotation/rotation.{create,read,update,delete,activationRequest}.js`, and for `user`: `services/user/user.{account,profile,points,teamRead,list}.js` plus the existing `user.team.js`, `user.teamTimeline.js`, `user.create.js`; the others still query models directly, see `docs/architecture/backend-structure-review.md`). The points-transfer model is `models/PointTransfer.js` (its registered name stays `Transaction`: collection `transactions`).
- Mail: `services/email/` (`email.transport.js` is the transport; `demand/` holds everything about substitution requests: `demand.emails.js` = the per-demand mails, `demand.changeNotifications.js` = who is told after a system change; the other mails sit at the top level) with MJML/Handlebars templates rendered by `services/email/email.renderer.js` (`/preview/:template` route for dev preview); `MAIL_SERVICE=console` logs instead of sending. Inbound mail parsed in `email.inbound.js`. When a team change or rotation change cancels a request or removes an accepter, third parties are notified **after the transaction commits** via `services/email/demand/demand.changeNotifications.js` (`notifyDemandChanges`). The mails are deliberately generic (no cause, no "automatic" wording): a removed accepter triggers the same `cancelledAcceptance` mail as a voluntary withdrawal, a cancelled request sends `demandCancelled` to its poster and/or accepter (cascade included). It never throws, skips users without an address and the acting user.
- Rules: `services/rule/` (predefined rules seeded at startup) configure per-center behaviour.

### Core domain (needs several files to understand)
Shifts are not stored per-day per-user; they are **computed** from `Rotation` (a cyclic pattern of `Shift`s per `Team`, activated via `services/rotation/rotation.activation.js`) plus overrides (`CalendarEntry`, `Variation`, `Substitution`, `Transaction`). A team's position in the rotation cycle comes from ONE formula in `services/team/team.cycleIndex.js` (`cycleDayIndex`, used by `computeShiftOfTeam`, `computeUserShifts`): start of cycle = `Center.cycleAnchorDate + Team.cycleOffset` days, falling back to the legacy `Team.cycleStartDate` when a team has no offset or the center no anchor (migration in progress: `cycleStartDate` is kept, never rewritten; `PUT /team/:id/cycle-start-date` keeps the offset in sync once a center is migrated). The teams page picks a team's position with a tile selector (`components/Teams/CycleDayPicker.vue`: one tile per rotation day with shift name and hours, the occupying team on taken days, a 14-day preview; choosing a taken day offers a swap) that calls `PUT /team/:id/cycle-position` (`{ day, date, swap }`, `services/team/team.cycle.js`: "at `date` the team is on rotation day `day`"; it writes the offset and the legacy date together, creates the center's anchor on first use, refuses two teams on the same day with code `CYCLE_POSITION_TAKEN` unless `swap` is true). Moving a team that already had a position rewrites its base shifts from today, so without `confirmed: true` the endpoint answers 409 `{ needsApproval, message, teams, members: [{ name, substitutions, entries }] }` when members (current, future and reinforcements) have open/accepted substitutions or shift-based calendar entries from today on; with `confirmed: true` it cancels those substitutions (or withdraws the accepter), deactivates the shift-based entries (`sanitizeUserPeriod`, one transaction) and emails the people concerned after commit (`notifyDemandChanges`); the front shows `CycleChangeImpactDialog.vue` with a "Forcer le changement" button. The teams page warns when the number of teams differs from the active rotation's days, and each rotation card on the rotation page warns when its days differ from the center's team count. Migrate existing centers with `node backend/scripts/migrateCycleOffsets.js` (dry-run by default; `--apply` writes only centers with no anomaly after checking old/new equivalence and saving a backup; `--rollback --apply` removes the new fields). The number of teams is meant to equal the number of rotation days. `computeUserShifts` resolves the active rotation per day (last activation <= that day), never once per batch. Helpers in `services/planning/` (`computeUserShifts`, `computeShiftOfTeam`, `findLatestRotation`, `generateShiftsMap`) and `utils/` (`getTeamAtDay`, `shifts/getEffectiveShiftTimes`, `shifts/shiftsOverlap`) do this computation; dates are center-timezone sensitive (`@js-temporal/polyfill`).

Compatibility of a demand or a switch with a user's planning (`services/substitution/compatibility/compatibility.categorize.js`; the pure rules are in `compatibility.rules.js`): `legalLimitsFor` applies every work rule and returns limit codes — `insufficientRest` (11h between shifts), `35limit` (35h continuous rest per 7-day window), `48hLimit`, `consecutiveDaysLimit` (max 5 consecutive days, the streak containing the target), and the night rules (a night control is any shift that works between 00:00 and 06:00 center time, `utils/shifts/nightControl.js`): `nightControlRestLimit` (12h rest after), `consecutiveNightLimit` (max 2 consecutive), `restAfterTwoNightsLimit` (48h after two); plus `alreadyWorking`. `categorize` (limits, `canSwitch`, rest, invalid windows; used by the user pool) and `getCompatibleSwitches` (`substitution.switches.js`) both go through it. Until a user (or the poster) chooses a variation the default hours are assumed; a chosen variation is always used (`categorize(demand, map, { selectedVariation })` simulates the choice). Trying every variation (`compatibleVariations`, `compatibleFetcherVariationsByDate`, `compatiblePairsByFetcherDate`, `potentiallyCompatible`, plus `variationsExplored`) is optional, **off by default**, and lives in `services/substitution/compatibility/compatibility.variations.js`: `categorizeWithVariations(demand, map, { explore })` (used where demand cards are displayed: `request.list.js`, `compatibilityService.js`), enabled per call or with `EXPLORE_VARIATIONS=true`. The whole flow, assumptions and result shape are in `docs/architecture/demand-categorization.md`. In this code a planning shift is `{ date: 'YYYY-MM-DD' (day it starts), startTime: 'HH:mm', endTime: 'HH:mm', endsNextDay }` with no timestamp: the hours are local hours of the user's center, and all shifts of a planning share that zone, passed as `timeZone` (`getCenterTimeZone` / `getUserTimeZone`). `withZonedBounds` (`utils/shifts/shiftTime.js`) turns them once into `Temporal.ZonedDateTime` (real durations, 7-day windows at local midnights, correct on clock-change days); `wallClockIso` writes an instant as the center's local time with a `Z`, which is what the front reads. Details: `docs/architecture/demand-categorization.md`, section "Time zones".

Substitutions (`services/substitution/`, split by action: creation, accept, cancel, withdraw, delete, list, cascade, expiry, pendingTransactions; `index.js` re-exports) let a user post a shift ("demand") that others accept/swap. `substitution.compatibility.js` and `substitution.switches.js` decide who can take it (overlap/rest/rules), and `services/substitution/compatibility/compatibility.categorize.js` categorizes demands for the requesting user (v1 was removed). Models: `Substitution`, `User`, `Team`, `Center`, `Rule`, `Ticket`, `Announcement`, `Message`.

Period cleanup for a user (e.g. after a team change): `services/user/user.sanitizePeriod.js` exports `cancelUserSubstitutionsInPeriod`, `clearUserCalendarEntriesInPeriod` and `sanitizeUserPeriod(userId, { from, to? })` (open-ended when `to` is omitted; both ends inclusive). Calendar entries are deactivated (`active: false`), never deleted, and no emails are sent.

Team ownership is stored as overlapping occurrences (`user.teams`: `{ teamId, fromDate, toDate|null }`, `toDate` inclusive; a bounded occurrence = reinforcement and beats the open-ended permanent one). `services/team/team.segments.js` turns them into contiguous segments (`buildTeamSegments`, `getOwnerTeamIdAt`) and diffs two segment lists (`diffTeamSegments` → `{ from, to, oldTeam, newTeam }`, inclusive bounds, `to: null` = unlimited, directly usable as a `sanitizeUserPeriod` period). `services/user/user.team.js` (`assignTeamToUser`, `deleteTeamOccurrence`) uses them: it diffs the segments, runs `sanitizeUserPeriod` on each changed period and saves `user.teams`, all in one transaction, and returns the `changes`. Without `confirmed`, if the change would cancel substitutions or deactivate calendar entries, it applies nothing and returns **409** `{ needsApproval, message, segments: { before, after }, teams: { id: name }, changes: [{ from, to, oldTeam, newTeam, substitutions, entries }] }` (built with `previewUserPeriodImpact`, the read-only twin of `sanitizeUserPeriod`); the client re-sends with `confirmed: true` (body for `POST /user/:id/assign-team`, `?confirmed=true` for `DELETE /user/:id/team-occurrences/:occurrenceId`). `assign-team` also accepts `replaceOccurrenceId` to swap an occurrence in one atomic change. Front: `apiFetch` turns any 409 into `{ ...data, needsApproval: true }` (no throw); `components/Profile/TeamChangeImpactDialog.vue` shows the before/after timeline and the affected items. For display, `buildTeamTimeline` returns the same segments tagged `kind: 'permanent' | 'reinforcement'` (an occurrence with a `toDate` is a reinforcement), served by `services/user/user.teamTimeline.js` as `GET /user/teams/:centerId/timeline` (every team's members, past/current/future, default window 3 months before and 9 months after today) and `GET /user/:id/team-timeline` (one user's teams), both guarded by `middleware/centerAuth.js` (same center, or master). The front only draws them: `components/Teams/TeamTimeline.vue` (generic horizontal timeline: permanent = primary, reinforcement = secondary + stripes, past dimmed, today line) is used by `TeamMembersList.vue` (team members drawer, falls back to the plain list if the timeline is unavailable) and `UserTeamCard.vue`.

`front/src/deprecated/` holds dead code being phased out (notifications were deprecated) — don't build on it. (`backend/deprecated/` and the other unused backend files were deleted; they remain in git history.)

## Front architecture

- File-based routing from `src/pages/` (`vue-router/vite`, typed routes in `typed-router.d.ts`) with layouts from `src/layouts/` (`vite-plugin-vue-layouts-next`). Components and Vue/vue-router APIs are auto-imported (`unplugin-vue-components`, `unplugin-auto-import`); `components.d.ts` / `auto-imports.d.ts` are generated — don't hand-edit.
- Data flow: page/component → Pinia store (`src/stores/*Store.js`) → API wrapper in `src/services/*Service.js` (one per backend resource, mirroring `/api/<resource>` routes) → backend. Keep service, store and backend route/controller in sync when changing an endpoint.
- `src/plugins/` registers Vuetify, router, Pinia; theming in `src/styles/settings.scss`. Shared dialogs/components live in `src/components` (e.g. a `baseDialog`).
- Team pages: `pages/center/[centerId]/teams.vue` (cards show the team's current cycle day, with buttons for the member timeline and for the grid) and `pages/center/[centerId]/grid.vue` (`?team=<id>&span=6|12|24`): a members × days grid (`components/Teams/TeamGrid.vue`, one cell per member per day, 6, 12 or 24 days from today in the center's time zone; mobile is limited to 6 days), fed by `GET /api/team/:id/grid?startDate&endDate` (`services/team/team.grid.js`, `authorizeTeamAccess`, 93 days max: the page loads the previous, current and next period in one call). It lists the team's current members and reinforcements (a reinforcement = a bounded occurrence) with, in each cell, only what departs from the team's usual shift (calendar entry, substitution or switch, variation, hour patch, off) as icon + name, an empty cell otherwise; the team's usual shift of each day (`teamShifts`, from `computeShiftOfTeam`) is shown once in the column header, and for a replacement or switch the other person's name. - Theme colour gotcha: `primary`, `secondary` (and a few others, see `src/plugins/vuetify.js`) are declared as 8-digit hex with an `ff` alpha, so Vuetify generates `--v-theme-primary: r,g,b,1` (four values). `rgb(var(--v-theme-primary))` works but `rgba(var(--v-theme-primary), 0.5)` is INVALID CSS (five values). Until the theme colours are written as 6-digit hex, apply an opacity with `color-mix(in srgb, rgb(var(--v-theme-primary)) 50%, transparent)`. The CSS variables use the project's camelCase keys (`--v-theme-onPrimary`), not Vuetify's kebab-case defaults.

- Dates: use **Temporal** (`@js-temporal/polyfill`, a dependency of both `backend/` and `front/`) for every calendar or time-zone computation (today in a center's `timeZone`, day arithmetic, comparisons, formatting between zones), in the backend and in the front. In the front always `import { Temporal } from '@js-temporal/polyfill'` explicitly, never use the bare global `Temporal`: recent browsers ship a native one, and mixing it with the polyfill breaks `instanceof` and Vue prop type checks ("Expected PlainDate, got Temporal.PlainDate"); the polyfill also covers Capacitor WebViews without native Temporal. Avoid new `Date` arithmetic, `setHours`, `toLocaleDateString({ timeZone })` tricks and string slicing for this; use `Temporal.Now.plainDateISO(tz)`, `PlainDate`, `ZonedDateTime`. `computeUserShifts` also follows it: `utils/dates/calendarDay.js` (`toCalendarDay`) turns any input into a `Temporal.PlainDate` in the user's center time zone (a plain `YYYY-MM-DD` or a UTC-midnight `Date` is a day taken as is, any other instant is placed in `Center.timeZone`), and `getTeamAtDay` / the rotation timeline compare days, reading stored `Date`s or `YYYY-MM-DD` strings alike so the stored fields can move to strings later without touching the readers. In the backend the cycle code follows this (`utils/dates/plainDate.js`: `toPlainDate`, `toMongoDate`, `eachDay`, `daysBetween`, `compareDays`, `todayIn`; the cycle formula is in `services/team/team.cycleIndex.js`; calendar days are `Temporal.PlainDate` and a `Date` only appears at Mongo boundaries; any incoming value is read as its UTC calendar day, so a legacy `cycleStartDate` stored with a time of day loses that time). Stored days are being moved from midnight-UTC `Date` fields to `YYYY-MM-DD` strings: each old field has a string twin next to it (`activationDates` -> `activationDays`, `User.teams[].fromDate/toDate` -> `fromDay/toDay`, `personalData.birthDate` -> `birthDay`, `posterShift.date` / `accepterShift.date` -> `posterShift.day` / `accepterShift.day`, `cycleAnchorDate` -> `cycleAnchorDay`; registry and `dayField` schema type in `utils/dates/dayFields.js`). All backend writers now write both fields and all readers read the day twin first, falling back to the old `Date` field with a throttled `[jours] ...` `console.error` when the twin is missing or inconsistent (`utils/dates/dayAccess.js`: `activationDaysOf`, `posterDayOf`, `shiftDayOf`, `occurrenceDays`, `birthDayOf`, `anchorDayOf` for reads, `dayFilter` / `dayInArrayFilter` for Mongo queries, `toDay` for writes). A `[jours]` line in the logs means unmigrated data or a writer that forgot the twin: run the script below. When writing a new place that stores or reads one of these days, use those helpers. In the front, `src/utils/dayFields.js` does the same for API data (`posterDay`, `accepterDay`, `occurrenceDays`, `birthDayOf`, `activationDay`, `formatDay`, `todayKey`): it reads the day twin first, then the old ISO field, and always returns a `YYYY-MM-DD` key; compare keys (`sameDateKey`, string comparison), never `Date` objects or ISO strings, and display with `formatDay` (no browser time-zone shift). Send keys to the API too: a Vuetify date-picker value (a `Date` at local midnight) goes through `pickerDayKey` (`utils/dateKey.js`), never `toISOString()`. The old `Date` fields stay the source of truth until the twins are the only fields read. Everything that disappears at cut-over is tagged `TEMPORARY(day-fields)` in a comment (`grep -rn "TEMPORARY(day-fields)" backend front/src`): tag any new code that only exists for the migration the same way, and delete every tagged item when the old fields are dropped. `node backend/scripts/migrateDayFields.js` fills and checks the twins (dry-run by default; `--apply --confirm=<db name>` writes after saving a backup; `--check` exits 1 if anything differs; `--rollback --apply` removes the twins; values with a time of day are anomalies unless `--truncate`). A native `Date` is only for what an API forces on you (Mongoose fields, Vuetify's date picker, `toISOString` on the wire): convert at that boundary (`new Date(plainDate.year, plainDate.month - 1, plainDate.day)`), and convert existing `Date` code to Temporal when you touch it, without refactoring unrelated code. Center time zone: `Center.timeZone` (default `Europe/Paris`), served by `GET /center`.
