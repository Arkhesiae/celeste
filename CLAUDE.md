# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Celeste is a shift-management / planning app (teams, rotations, shift substitutions between users, tickets, announcements) for "centers". Two parts, deployed together:

- `backend/` — Node 20, Express 5, Mongoose 9 (MongoDB), ES modules (`"type": "module"`). Code comments, logs and user-facing messages are largely in French.
- `front/` — Vue 3 (Composition API, `<script setup>`), Vuetify 4, Pinia stores, Vite, Capacitor (Android/iOS wrapper).

Cursor rule (`.cursor/rules`): always provide solutions that consider the full front-to-back workflow, and always use the Vue Composition API with `<script setup>`.

## Commands

Backend (`cd backend`):
- `npm run dev` — nodemon `server.js`; `npm start` — plain node
- `npm run format` — prettier on `src/**`
- `npm test` runs `node --test`: `test/compatibility.rules.test.js` (pure rest / workload rules against an independent oracle; tests marked `todo` describe known defects, see `docs/quality/blocking-issues.md` #47) and `test/compatibility.db.test.js` (`getCompatibleSwitches` on a scratch database `TEST_MONGO_URI`, default `mongodb://127.0.0.1:27017/celeste_test_compat`, dropped before and after, skipped when MongoDB is unreachable). No other test suite exists.

Front (`cd front`):
- `npm run dev` (or `npm run front` for `--host`), `npm run build`, `npm run lint` (eslint --fix), `npm run lint:check` (eslint, no write), `npm run format` / `format:check` (prettier on `src/**`, `.prettierrc.json`: ESLint owns correctness, Prettier owns layout; `vue/component-api-style` enforces `<script setup>`; the first whole-codebase `format` is a separate commit, about 260 files differ today)
- Capacitor: `npm run cap:sync`, `cap:open:android`, `cap:open:ios`

Local setup (see CONTRIBUTING.md, marked incomplete): create `front/.env.local` (`VITE_API_URL=http://localhost:3000/api`, `VITE_NODE_ENV`, `VITE_ADMIN_MAIL`, `VITE_ADMIN_PASS`) and copy `backend/.env.example` to `backend/.env` (the only file the backend loads, via `import 'dotenv/config'`; `.env.development` is not read): every variable the code reads is listed there with its default and whether it is required (`MONGO_URI`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `FRONT_URL`, `FRONTEND_URL`, `PORT`, `LOCAL_ADMIN_PASSWORD`, `SES_*`, ...). Needs a local MongoDB **replica set** (`docker compose -f backend/docker-compose.dev.yml up -d`). Mails are only printed to the console ("Mail simulé", `simulated: true` in the result) unless `NODE_ENV=production` (always real, through SES, whatever `MAIL_SERVICE` says) or `MAIL_SERVICE=ses` (a test server that must really send); `EMAIL_PORT` (default 587) is the SMTP port of both transporters. Optional: `GEOCODER_URL` (default `https://nominatim.openstreetmap.org/search`) and `GEOCODER_USER_AGENT` (default `Celeste-app/1.0`) for the center map geocoding (see Center routes below); `EXPLORE_VARIATIONS=true` turns on the exploration of ambiguous shift variations in demand lists (off by default, see `docs/architecture/demand-categorization.md`).

Deploy: root `Dockerfile` builds `front` and copies `dist` into `backend/public`, so one Express container serves both API and SPA. `docker-compose.yml` adds mongo, nginx, certbot, a backup job (`scripts/backup_mongo.sh`) on an external `celeste` network, using `.env.prod`.

## Backend architecture

Layering: `routes/` → `controllers/` → `services/` → `models/` (+ `utils/` for pure helpers, `bootstrap/` for the admin seed run at startup, `dev/` for development fixtures called by the dev-only `/api/dev` routes). Pure helpers live in `utils/`: `dates/` (Temporal day helpers, see Dates below), `ids.js` (`sameId`, `idOf`, `isValidId` — never compare ids with `===` or `.toString() ===`), `names.js` (`fullName`, `shortName`), `mongo.js` (`inTransaction(fn, { session })`, `findOrThrow(Model, id, { message, select, populate, session })`), `math.js` (`mod`), `shifts/` (shift hours, night control). Domain computations that read the database live in `services/planning/` (`computeUserShifts`, `createTeamShiftReader`, `generateShiftsMap`), `services/rotation/rotation.timeline.js` (`findLatestRotation`, and the one rule for the rotation in force on a day, `activationTimelineOf` / `activationAt`, which the activation change preview and conversion of `rotation.activation.js` use too), `services/team/` (`team.cycleIndex.js`, `team.segments.js`, `team.atDay.js`: cycle formula, team occurrences, owner team of a day) and `services/demand/` (`compatibility/compatibility.rules.js`, `compatibility/compatibility.categorize.js`, `compatibility/compatibility.variations.js`, `demand.userPool.js`); `services/center/center.timezone.js` gives a center's time zone. Use these helpers instead of writing new local copies.

- Configuration: environment variables are read where they are used (`process.env.X`), and the `.env` file is loaded once by `import 'dotenv/config'`, the first import of `server.js` (so the other modules see it). `backend/config/` holds the **constants** (policy numbers, durations, limits) shared by the backend, one file per topic, each value documented: `points.js` (`MIN_POINTS_BALANCE`, `MAX_POINTS_TO_ACCEPT_REQUEST`, `SHIFT_POINTS_PER_HOUR`, `SHIFT_BASE_POINTS`), `auth.js` (`DEFAULT_ACCESS_TOKEN_EXPIRY`, `REFRESH_TOKEN_DAYS` / `REFRESH_TOKEN_EXPIRY` / `REFRESH_TOKEN_MAX_AGE_MS`, `OTP_VALIDITY_MS`; the token secrets `JWT_SECRET` / `JWT_REFRESH_SECRET` are read straight from `process.env` where tokens are signed and verified, with no fallback value, so they must be set (the `test/*.db.test.js` files that sign tokens default them to a test value)), `limits.js` (body and avatar sizes, maximum periods of the date-range endpoints), `schedules.js` (cron expressions, `DEFAULT_REMINDER_HOUR`), `server.js` (`DEFAULT_PORT`, MongoDB connection retries), `paths.js` (`PUBLIC_DIRECTORY`, `AVATARS_DIRECTORY`), `workRules.js` (legal rest and workload thresholds of the compatibility computation), `compatibility.js` (planning radius, variation exploration bounds), `geocoding.js` (geocoder pause, timeout, retry delay). Put a new shared constant there instead of redefining it in a file; a value that only one file uses and that is not a policy number stays local. Avatars uploaded by users live in `backend/public/avatars/`, which is **not tracked by git** (created at startup, keep it in a volume in production).
- `server.js`: CORS (explicit origin allowlist incl. `capacitor://` origins), mounts `routes/index.js` under `/api`, serves `public/` (the built SPA, with catch-all for non-`/api` paths) and `/api/avatars`, then `errorHandler` last. On Mongo connect (5 retries) it runs `initializeRules()`, `createAdmin()`, `createLocalAdmin()` before listening.
- Errors: **never answer an error with `res.status(4xx/5xx).json(...)`** and never build a custom error shape. Validate and `throw new AppError(message, status, code?)` (`error/AppError.js`); in a `try/catch` just call `next(error)` (handlers take `(req, res, next)`; in a promise chain use `.catch(next)`). `middleware/errorHandler.js` is the single place that decides what the client sees, as `{ error, message, code }` (both `error` and `message` are set because the front reads either): an `AppError` is returned as is; framework 4xx errors (invalid JSON, payload too large) and `MulterError` (400) pass through; **anything else becomes a generic 500 (`Erreur interne du serveur`)** and is only logged, so raw Mongoose/driver text never reaches clients. Consequently, an error whose message the user must see has to be an `AppError` with its status in the service/util that detects it (a plain `Error` with a `.status` property is *not* honoured), and controllers must not match on `error.message`. Do not use 409 for plain errors: the front `apiFetch` treats a 409 as an approval request (`needsApproval`) and does not throw. Auth uses `middleware/authMiddleware.js` (Bearer JWT → `req.user`; `isAdmin` etc.). Auth flows (login, refresh token, password reset, OTP, account recovery) live in `services/auth/`.
- Center routes (`routes/center.routes.js`): only `GET /center` is public (sign-up, account recovery and contact forms need the list before an account exists) and it returns just `_id, name, OACI, type, zone, timeZone` (`timeZone` is public on purpose: the activation date picker needs it to grey out past days); everything else requires a token — create/update/delete and the cross-center reads (`/admins`, `/users/count`, `/all-active-rotations`) are master-admin only, `/:id/active-rotation` is limited to members of that center (`authorizeCenterParam`).
- Centers map (dashboard): `GET /center/map` (any logged-in user, `services/center/center.map.js`) returns, for every non-deleted center that has a position, `{ _id, name, OACI, type, latitude, longitude, open, accepted, isOwn }` where `open` / `accepted` count the center's upcoming demands (day of the original shift today or later in that center's time zone) and `pendingLocations` counts centers still without a position. It is cross-center on purpose and returns counts only (no demand content, no person). Positions are found **from the center name** by `services/center/center.geocode.js` (Nominatim, tries `<name>` then `aéroport <name>`, one lookup per second as the usage policy asks, a descriptive User-Agent), stored once in `Center.location` (`latitude`, `longitude`, `displayName`, `geocodedAt`), and a name that finds nothing is remembered in `Center.locationLookupFailedAt` and retried after 7 days. Lookups run in the background from the map request (`ensureCenterLocations`, never awaited, one at a time), so a first call may return fewer centers; renaming a center (`PUT /center/:id`) clears its position. The public `GET /center` does not expose the position. Front: `components/Dashboard/CentersMapCard.vue` (Leaflet loaded on demand, about 43 kB gzip in its own chunk). **No tile service** (those need keys or can disappear): the background is a local GeoJSON of country outlines, `src/assets/map/countries.json` (Natural Earth, public domain; precise in Europe, coarse elsewhere; about 98 kB gzip, lazy), generated by `npm run map:build` (`scripts/buildMapData.mjs`, from the dev dependencies `world-atlas` and `topojson-client`) and drawn as SVG by Leaflet; sea, land and pins are colored through `--v-theme-*` CSS classes (`cm-*`), so they follow the Material 3 theme, light or dark (primary = open demands, secondary = only taken, surfaceVariant = none, a ring on the user's own center).
- Access control: a route is **public only if a screen needs it before login** (sign-up, login, contact form, landing): `GET /center`, `GET /team/public/:centerId`, `GET /user/info/:email`, `POST /user/create|check-email`, `POST /otp/*`, `POST /ticket/create`, `GET /stat*`, plus auth and the dev-only `GET /user/devlist` (404 in production); each returns the strict minimum. Everything else needs `verifyToken` **and a center guard** from `middleware/centerAuth.js` (master admin everywhere, everyone else only inside their own center, fail-closed): `authorizeCenterParam('centerId')` for a center in the URL (`authorizeCenterQuery` for the one read whose address cannot change, `GET /rule?centerId=`: another center is refused except for the master admin) — **the target center always goes in the URL (`/center/:centerId/...`), never in the body**, so the access rule is readable from the route and a spoofed body field changes nothing (creations are `POST /rotation/center/:centerId`, `POST /team/center/:centerId`, `POST /announcement/center/:centerId/send`; the global announcement `POST /announcement/send` is master-only), `authorizeResourceCenter(Model, { centerField, masterOnlyField })` or its instances `authorizeDemandAccess` / `authorizeTeamAccess` / `authorizeTicketAccess` / `authorizeRotationAccess` / `authorizeBannerAccess` for a resource by id (`masterOnlyField` makes a flagged resource master-only, e.g. `isGlobal` banners), `authorizeBodyResourcesCenter` for id lists, for users `authorizeTargetUserCenter` (self or colleague) and `authorizeSelfOrCenterAdmin` (self or the center's admin; put `isAdmin` in front for admin-only routes), and `resolveCenterId` for list routes that only need the caller's center in `req.user.centerId`. The caller's role and center are read from the JWT access token in one place (`loadCaller`; `centerId` is put in the token at login and refresh by `generateAccessToken`, so a change of center or role applies at the next token refresh, 15m by default, and a deleted user is not rejected by the guards until the token expires), and error texts are generic on purpose (no per-entity wording). `isAdmin` alone is **not** enough to act on a resource. The old `isUserOrAdmin` / `checkUserCenter` were removed (any admin could act on any user; the latter failed open).
- Account status (`middleware/userStatus.js`): `verifyToken` (`middleware/authMiddleware.js`) is an **array** `[verifyAccessToken, verifyUserActive]` (`router.use(verifyToken)` and `router.get(path, verifyToken, ...)` take it as is), so every authenticated route re-reads the account in the database (the JWT lives 15 min and says nothing about a recent deactivation), answers **403 `ACCOUNT_INACTIVE`** for a deactivated (`User.isActive === false`) or deleted account, and hands the account to the next middleware in `req.accountStatus`. `hasNoPendingCenterTransfer` is put on the routes that mutate (see "Route file layout": one `router.use` before the writes of `team`, `demand` and `calendarEntry`, per route in `user`) teams, points, demands or planning (`POST /team/center/:centerId`, `PUT /team/:id/{cycle-position,name}`, `PUT /team/order`, `DELETE /team/:id`, `POST /user/:id/assign-team`, `DELETE /user/:id/team-occurrences/:occurrenceId`, `POST /user/:id/points/transfer`, `POST /demand` and `/:id/{interest,accept,swap,cancel,withdraw,send-email}`, `POST /calendar-entry/{register-entry,undo-mods,delete-assignment}`); it reads `req.accountStatus` (no query) and answers **403 `CENTER_TRANSFER_PENDING`** to a user with `User.pendingCenterTransfer` set. Reads carry no such middleware, so that user can read; profile, preferences, tickets and messages are not guarded either. Add the middleware to any new route that mutates teams, points or demands. `loginUser` (after the password check) and `refreshAccessToken` call `assertUserActive`, so an inactive account cannot log in or renew its token, while a user with a pending transfer logs in normally. `pendingCenterTransfer` is created by the center transfer flow below; the front has no rejection dialog for `ACCOUNT_INACTIVE` (known issue #52). Tests: `test/userStatus.test.js`, `test/accountStatus.db.test.js`, `test/centerTransfer.db.test.js`.
- Route file layout (`routes/*.routes.js`): public routes first (only those a screen needs before login), then **one** `router.use(verifyToken)` for everything below (no `verifyToken` repeated on each route; a file whose routes are all authenticated starts with it), then the reads, then the writes, and inside a file the routes are ordered by access level: any logged-in user, then `router.use(isAdmin)`, then `router.use(isMasterAdmin)` (each `use` applies to everything below it, so a role guard is written once per section, not on every route; a resource guard such as `authorizeTeamAccess` stays on its route because it depends on the path, except where every `:id` of a file is the same resource: `ticket`, `demand`, `rotation` and `team` routes have one `router.param('id', authorizeTicketAccess | authorizeDemandAccess | authorizeRotationAccess | authorizeTeamAccess)`, which runs after the `use` guards (roles, pending transfer) and before the handler, for every route with an `:id`, `DELETE /:id` of a ticket included). That rule fixes the meaning of `:id` in such a file: a centre in the URL is always `:centerId` (so `GET /team/:centerId`, not `/:id`). In `team.routes.js` and `demand.routes.js` the writes come after a single `router.use(hasNoPendingCenterTransfer)`, so **order matters there**: a read declared below that line would be refused to a user with a pending center transfer. A read is a GET (filters in the query string, like `GET /demand/center/:centerId/heatmap?startDate&endDate`); a POST that only reads is kept only when it has a side effect (`POST /demand/center` and `/:id/consult` mark demands as seen) or a body too big for a URL (`POST /demand/recategorize`, a list of ids), and its route says so in a comment. A path declared before a same-shaped parameter route (`/:id`) of the same method must stay before it.
- Serialization: `models/User.js` strips `password`, `refreshTokens`, `resetPasswordToken` and `resetPasswordExpires` from `toObject()`/`toJSON()`, so no endpoint can leak them by returning a user; they stay readable on the document for the auth flows. Never rely on a controller to remember to delete them.
- "Active rotation" always means the one of the **center's current day** (`todayIn(centerTimeZone)`), never the UTC day: `GET /rotation/status/:centerId` (`listRotationsWithStatus`, statuses `active` / `toBeActive` / `past`, compared as `YYYY-MM-DD` days, read by the dashboard `ActiveRotationCard`), `GET /center/:id/active-rotation` and `GET /center/all-active-rotations` (`findLatestRotation` given that day). Around midnight a center ahead of UTC (Paris) switches rotation up to a few hours before the UTC date changes.
- Rotation mutations (`routes/rotation.routes.js`) are guarded by `authorizeRotationAccess` (in `middleware/centerAuth.js`; creation uses `authorizeCenterParam`): a local admin can only touch rotations of their own center (master admin: all; fail-closed when the center is missing). A center cannot have two activations on the same date (adding one answers 400 `ROTATION_ACTIVATION_DATE_TAKEN`), and a new activation must be today or later in the center's time zone (400 `ROTATION_ACTIVATION_DATE_PAST`). Activation dates only change through `POST /rotation/:id/activate` and `POST /rotation/:id/remove-date` (one endpoint each: without `confirmed: true` in the body they only preview and answer 409 `{ needsApproval, changes }` when requests are affected; with a boolean `confirmed: true` they apply — the front calls `rotationService.setActiveRotation(id, date, confirm)` / `removeActivationDate(id, date, confirm)`, and the store takes `{ confirm }`), which cancels or converts the affected demands inside one transaction; `PUT /rotation/:id/update` only renames, and `PUT /rotation/:id/day` (body `{ updatedDay, confirmed }`) is free only on a rotation that was never activated (no activation date, shown on its card with a "Jamais activé" chip and a dashed border); with any activation date it writes nothing and answers 409 `{ needsApproval, message }` unless `confirmed: true`, a **provisional bypass** that rewrites past plannings and demand hours (known issue #68). A deleted rotation is a 404. The past is not editable: a past activation date cannot be removed (400 `ROTATION_ACTIVATION_DATE_PAST`; an unknown date is a 404), and a rotation cannot be deleted while active or with upcoming activations (`ActiveRotation`, `RemainingOccurences`, judged on the center's day). Deletion is soft and **leaves the past alone**: a deleted rotation gets no card and cannot be activated, but `findLatestRotation`, the planning timeline (`planning.userShifts.js`), the activation timeline of `rotation.activation.js` and `sortedRotations` of `listRotationsWithStatus` still read it, so **do not filter rotations on `deleted` when resolving a day**; removing today's activation is refused when the one that would take over is deleted (400 `ROTATION_PREVIOUS_DELETED`). The timeline only offers to remove today's and later dates. Test: `test/rotationGuards.db.test.js`.
- Cron: `jobs/` (imported by `server.js`) uses node-cron; `demandJob` every 30 min cancels past demands and completes/archives finished ones via `services/demand/demand.expiry.js` (a demand is past when its day is before today **in its center's time zone**); `transactionJob` runs scheduled transactions (`services/transaction/`). `reminderJob` (hourly) sends the accepter of a replacement/switch a reminder the evening before (`services/demand/demand.reminder.js` → `sendReplacementReminderEmail`): "tomorrow" and the send hour are evaluated in each center's `timeZone`, from `REMINDER_HOUR` (default 18) local time; `Demand.reminderSentAt` is claimed atomically before sending (released if the send fails) and reset to `null` whenever a request is accepted, so each accepter is reminded once. The accepter's email preferences (`all` and the `replacement`/`switch` category) are respected.
- Naming: route files `<resource>.routes.js` and controllers `<resource>.controller.js` are both singular and camelCase like the models and service folders (`calendarEntry.routes.js`, `accountRecovery.controller.js`, `services/calendarEntry/`; kebab-case is for URLs only, `/calendar-entry`), and `models/` and `services/` use the same singular word; **URL mounts are singular too** (`/api/user`, `/team`, `/rotation`, `/rule`, `/message`, `/ticket`, `/announcement`, `/banner`, `/stat`, `/calendar-entry`, `/center`, `/demand`; some sub-paths still name a plural, e.g. `/center/users/count`, `/user/teams/:centerId`), set in `routes/index.js` and called by `front/src/services/*Service.js`; **exports are named** in controllers, services and utils (group them with `import * as x from`; `export default` only for models and routers); **each `services/<domain>/` has an `index.js`** (`export *` of its files) that code outside `services/` (controllers, jobs, `server.js`, scripts, dev) imports, while files inside `services/` import the target file directly (a barrel between services creates import cycles), so a new service file is added to its domain's `index.js` and an exported name must stay unique inside the domain; **import style**: a controller imports each service domain once, as a namespace (`import * as rotationService from '../services/rotation/index.js'`, called `rotationService.createRotation(...)`, alias `<domain>Service`), after its other imports in the order libraries, `config`, `models`, `utils`, `error`, `services`, other controllers; a route file puts all its imports (libraries, `config`, `middleware` by name, `models`, then the controller as `import * as <resource>Controller`) above `const router = express.Router();` and registers handlers as `<resource>Controller.handler`; service files are `<domain>.<action>.js` (`rotation.create.js`, `demand.accept.js`, and also the mails `email.otp.js` / `demand.emails.js` and the planning computations `planning.userShifts.js`, `planning.teamShift.js`, `planning.shiftsMap.js`; `<domain>.service.js` is accepted for a small domain with a single file: `banner`, `rule`, to be split by action when it grows). Controllers read **and validate** the request (shared checks in `utils/validation.js`: `assertId`, `assertEmail`, `assertDay`, `assertPositiveInteger`, `assertObject`, each throwing a 400 `AppError`; business rules stay in the services), call a service in `services/<domain>/` and answer, with one response shape: a read (GET) returns the resource itself without envelope, a write returns `{ message }` plus the resource the client needs (`user`, `preferences`, `changes`...), a change that needs approval returns 409 `{ needsApproval, ... }`; controllers do not log errors (`errorHandler` does) and do not rewrap service errors (done for `rotation`: `services/rotation/rotation.{create,read,update,delete,activationRequest}.js`, and for `user`: `services/user/user.{account,profile,points,teamRead,list}.js` plus the existing `user.team.js`, `user.teamTimeline.js`, `user.create.js`; the others still query models directly, see `docs/architecture/backend-structure-review.md`). The points-transfer model is `models/PointTransfer.js` (its registered name stays `Transaction`: collection `transactions`).
- Center deletion is `services/center/center.delete.js` (`deleteCenter`): rotations and teams soft-deleted, users detached with their past teams kept (`endTeamMembership`). It uses **no transaction on purpose** (a standalone production `mongod` would refuse it, known issue #21) and marks the center deleted **last**, so that a failed deletion leaves the center visible and running it again completes it: keep that order, and keep each step safe to repeat. Test `test/centerDelete.db.test.js`.
- Center transfer (`routes/centerTransfer.routes.js` at `/center-transfer`, `controllers/centerTransfer.controller.js`, `services/centerTransfer/`): a user asks to join another center from the parameters page (`TransferRequestDialog.vue`: center + reason, then a confirm step that shows what will be wiped and, if `points < 0`, an error alert the user can pass), stored as `User.pendingCenterTransfer` (`POST /center-transfer`; the identity is the token's, never the URL; `GET /center-transfer/preview` gives `{ demands, entries, points, negativePoints }` for the confirm step, `GET /center-transfer/mine` the pending request, `DELETE /center-transfer` cancels it). While pending, `hasNoPendingCenterTransfer` freezes teams, points and demands, but the user logs in, reads and can cancel. Admins read the requests with `GET /center-transfer` (`components/Users/UserMutations.vue`, tab "Mutations" of `components/Users/UsersSections.vue`, at `/center/users/mutations`): those arriving in their center (`direction: 'incoming'`, `canAccept`) and those leaving it (`'outgoing'`, read only); the master sees and accepts all. `POST /center-transfer/:userId/accept` is for the admin of the receiving center (or the master; the service refuses anyone else with 403) and, in one transaction, sanitizes the upcoming period from today in the departure center's time zone (`sanitizeUserPeriod`: demands cancelled or withdrawn, shift-based calendar entries deactivated), cancels the user's pending deferred point transfers, sets `centerId`, ends their team membership (`endTeamMembership`, past teams kept), sets `points` to 0 and clears the request (a local admin loses the admin role); the people touched are emailed after the commit (`notifyDemandChanges`). The user's token keeps the old center until its next renewal (15 min). The receiving admin cannot refuse, **on purpose**: only the user cancels (do not report it as missing).
- Banners (dashboard messages written by admins, formerly "public announcements"; the separate `announcement` domain is the center mailing): `models/Banner.js` (its collection keeps the old name `publicannouncements` so no data migration), `services/banner/`, `controllers/banner.controller.js`, `routes/banner.routes.js` mounted at `/banner`. `GET /banner/active` (any logged-in user) returns `{ permanentBanners, nonPermanentBanners }` for the user's scope (global, or their center), without expired or inactive ones and, for non-permanent ones, without those the user acknowledged (`POST /banner/:id/acknowledge`); management (`GET|POST /banner`, `PUT|DELETE /banner/:id`) is for admins: a local admin only creates and edits banners of their own center and `GET /banner` lists the global ones and theirs (a global banner is master-only to edit, `authorizeBannerAccess`). Front: `stores/bannerStore.js`, `services/bannerService.js`, `components/Dashboard/BannerList.vue` (shown at the top of the dashboard), admin page `pages/admin/banners.vue`. Test: `test/banner.db.test.js`.
- Mail: `services/email/` (`email.transport.js` is the transport; `demand/` holds everything about demands: `demand.emails.js` = the per-demand mails, `demand.changeNotifications.js` = who is told after a system change; the other mails sit at the top level) with MJML/Handlebars templates (`templates/base.mjml` = envelope with header and footer, `templates/content/<name>.mjml` = one mail, a list of `<mj-section>`, `templates/partials/*.mjml` = shared pieces: `{{> hello }}`, `{{> title text="..." }}`, `{{> button href=... label=... }}`, `{{> demand }}`, `{{> contact person=... label=... }}`: a card with the other person's name, email and, if set, phone, as `mailto:` / `tel:` links; `person` is `contactOf(user)` from `demand.emails.js`, null without an address; every demand mail that has a counterpart carries it: `posterContact`, `accepterContact`, or `counterpartContact` for `systemCancel`, so the queries behind these mails must select `email personalData.phoneNumber`) rendered by `services/email/email.renderer.js` in two steps (Handlebars fills and escapes the data, MJML turns it into email HTML; `renderMail(name, data)`, `listTemplates()`; compiled templates are cached only when `NODE_ENV=production`, so a change shows on reload in dev; `formatText` escapes user text and turns line breaks into `<br>`). The look follows the site: dark header and footer (`#0F1416`, primary `#b4b3f5`, secondary `#e2ff6e`, the dark theme of `front/src/plugins/vuetify.js`) with radar rings and lines, light body (`#675496`, tiles `#f0f4f6`) readable in every client. ### Core domain (needs several files to understand)
Shifts are not stored per-day per-user; they are **computed** from `Rotation` (a cyclic pattern of `Shift`s per `Team`, activated via `services/rotation/rotation.activation.js`) plus overrides (`CalendarEntry`, `Variation`, `Demand`, `Transaction`). A team's position in the rotation cycle comes from ONE formula in `services/team/team.cycleIndex.js` (`cycleDayIndex`, used through `createTeamShiftReader()` of `planning.teamShift.js`, the lookup of a team's rotation shift on a day shared by `computeUserShifts` and the team grid: create one per batch; it reads each center, timeline and rotation once, and what it caches must be real promises (`exec()`), since a Mongoose query can only be awaited once): start of cycle = `Center.cycleAnchorDate + Team.cycleOffset` days, falling back to the legacy `Team.cycleStartDate` when a team has no offset or the center no anchor (migration in progress: `cycleStartDate` is kept, never rewritten; the only way to move a team is `PUT /team/:id/cycle-position`, which writes both). The teams page picks a team's position with a tile selector (`components/Teams/CycleDayPicker.vue`: one tile per rotation day with shift name and hours, the occupying team on taken days, a 14-day preview; choosing a taken day offers a swap) that calls `PUT /team/:id/cycle-position` (`{ day, date, swap }`, `services/team/team.cyclePosition.js`: "at `date` the team is on rotation day `day`"; it writes the offset and the legacy date together, creates the center's anchor on first use, refuses two teams on the same day with code `CYCLE_POSITION_TAKEN` unless `swap` is true). Moving a team that already had a position rewrites its base shifts from today, so without `confirmed: true` the endpoint answers 409 `{ needsApproval, message, teams, members: [{ name, demands, entries }] }` when members (current, future and reinforcements) have open/accepted demands or shift-based calendar entries from today on; with `confirmed: true` it cancels those demands (or withdraws the accepter), deactivates the shift-based entries (`sanitizeUserPeriod`, one transaction) and emails the people concerned after commit (`notifyDemandChanges`); the front shows `CycleChangeImpactDialog.vue` with a "Forcer le changement" button. The teams page warns when the number of teams differs from the active rotation's days, and each rotation card on the rotation page warns when its days differ from the center's team count. Migrate existing centers with `node backend/scripts/migrateCycleOffsets.js` (dry-run by default; `--apply` writes only centers with no anomaly after checking old/new equivalence and saving a backup; `--rollback --apply` removes the new fields). The number of teams is meant to equal the number of rotation days. `computeUserShifts` resolves the active rotation per day (last activation <= that day), never once per batch. Helpers in `services/planning/` (`computeUserShifts`, `createTeamShiftReader`, `findLatestRotation`, `generateShiftsMap`) and `utils/` (`getTeamAtDay`, `shifts/getEffectiveShiftTimes`, `shifts/shiftsOverlap`) do this computation; dates are center-timezone sensitive (`@js-temporal/polyfill`).

Compatibility of a demand or a switch with a user's planning (`services/demand/compatibility/compatibility.categorize.js`; the pure rules are in `compatibility.rules.js`): `legalLimitsFor` applies every work rule and returns limit codes — `insufficientRest` (11h between shifts), `35limit` (35h continuous rest per 7-day window), `48hLimit`, `consecutiveDaysLimit` (max 5 consecutive days, the streak containing the target), and the night rules (a night control is any shift that works between 00:00 and 06:00 center time, `utils/shifts/nightControl.js`): `nightControlRestLimit` (12h rest after), `consecutiveNightLimit` (max 2 consecutive), `restAfterTwoNightsLimit` (48h after two); plus `alreadyWorking`. `categorize` (limits, `canSwitch`, rest, invalid windows; used by the user pool) and `getCompatibleSwitches` (`demand.switches.js`) both go through it. Until a user (or the poster) chooses a variation the default hours are assumed; a chosen variation is always used (`categorize(demand, map, { selectedVariation })` simulates the choice). Trying every variation (`compatibleVariations`, `compatibleFetcherVariationsByDate`, `compatiblePairsByFetcherDate`, `potentiallyCompatible`, plus `variationsExplored`) is optional, **off by default**, and lives in `services/demand/compatibility/compatibility.variations.js`: `categorizeWithVariations(demand, map, { explore })` (used where demand cards are displayed: `demand.list.js`, `compatibilityService.js`), enabled per call or with `EXPLORE_VARIATIONS=true`. The whole flow, assumptions and result shape are in `docs/architecture/demand-categorization.md`. In this code a planning shift is `{ date: 'YYYY-MM-DD' (day it starts), startTime: 'HH:mm', endTime: 'HH:mm', endsNextDay }` with no timestamp: the hours are local hours of the user's center, and all shifts of a planning share that zone, passed as `timeZone` (`getCenterTimeZone` / `getUserTimeZone`). `withZonedBounds` (`utils/shifts/shiftTime.js`) turns them once into `Temporal.ZonedDateTime` (real durations, 7-day windows at local midnights, correct on clock-change days); `wallClockIso` writes an instant as the center's local time with a `Z`, which is what the front reads. Details: `docs/architecture/demand-categorization.md`, section "Time zones". Switch candidates (`getCompatibleSwitches(day, userId)`, `GET /demand/compatible-switches/:date`, used by the switch tile list of `DemandForm`; `day` is a `YYYY-MM-DD` string that the controller validates with `isValidDate` (400 otherwise), the service converts nothing): for each work shift of the rotation active that day it returns the result for the default hours (`limit`, `compatible`) and `variations: [{ _id, name, startTime, endTime, endsNextDay, limit, compatible }]`, each variation evaluated on its own hours with the same `legalLimitsFor`; the variation the user chose for the shift they give away is not used (the candidate replaces that day), only their other days count, with their real hours. The tile lists the variations, struck through when a rule refuses them (hours and reason as tooltip). Tests: `test/compatibility.db.test.js` (each variation against the independent oracle, and the user's own variation changing nothing).

**Declaration reminders**: in the demand modal (`components/Demands/DemandCards/DemandModal.vue`), an accepted demand shows to its poster and its accepter two two-state tiles, "OLAF renseigné" (OLAFATCO) and "ICNAGENDA renseigné" (ICNAGENDA), built like the assignment tiles (global `.tile`, `aria-pressed`, icon, title, subtitle that follows the state); the state is local and not stored (back to "not done" when the demand changes), no backend yet. Demands (`services/demand/`, split by action: `demand.{creation,accept,cancel,withdraw,delete,list,cascade,expiry,pendingTransactions}.js`; `index.js` re-exports) let a user post a shift that others take. **One name for the concept: "demand"** (model `Demand`, `/api/demand`, `demandStore`, `demandService`, `components/Demands/`, "Demande" in the UI). A demand has a `type`: `substitution` (replacement, for points), `switch` (swap of shifts) or `hybrid` (both offered). Do not call the umbrella "substitution" or "request" (a request is the HTTP request or a centre-transfer request). "Substitution" survives only as the replacement `type` value, as the planning effect of an accepted demand (`Assignment` `subType: 'substitution'`, `Assignment.substitution`, the `substitution` key of a day of `computeUserShifts`, `/user/:id/get-shifts-with-substitutions`) and in the lists named after a type (`availableSubstitutions`, `ownPendingTrueSubstitutions`); the MongoDB collection of `Demand` keeps its old name `substitutions` (`collection` option, no data migration). `demand.compatibility.js` and `demand.switches.js` decide who can take it (overlap/rest/rules), and `services/demand/compatibility/compatibility.categorize.js` categorizes demands for the requesting user (v1 was removed). Models: `Demand`, `User`, `Team`, `Center`, `Rule`, `Ticket`, `Announcement`, `Message`.

Work check of a user's planning (`GET /api/user/:id/work-check?from&to`, `authorizeSelfOrCenterAdmin`, 62 days max, `WORK_CHECK_MAX_DAYS` / `WORK_CHECK_MARGIN_DAYS` in `config/limits.js`; `services/user/user.workCheck.js`: `analyzeWork`, `getWorkCheck`): computes the shifts of `[from-7, to+7]` with `computeUserShifts` and returns, per day, the worked minutes (attributed to the day the shift starts, a night counts fully), the shifts and the rest before the first shift (`{ minutes, requiredMinutes, ok }`, 11h / 12h after a night control / 48h after two nights), and every sliding 7-day window (`workMinutes`, `longestRestMinutes`, `workOk` <= 48h, `restOk` >= 35h) plus the `limits`. It reuses the helpers exported by `compatibility.rules.js` (`windowStartingOn`, `longestRestIn`, `workMinutesIn`), so the calendar and the compatibility computation cannot disagree. An assignment with its own hours (training, office, stage... but not leave, absence or substitution) counts as a worked day (`computeUserShifts` gives every day an `isWorked`, computed once by `computeIsWorked` in `planning.userShifts.js`; it is not `presence`, which says whether the agent is at what they hold and drives the display. Worked = a work shift, except an optional rotation day nothing confirms (an assignment, or a `pres`, `variation` or `vic` modification: choosing a variation or VIC means the agent works it), a `vic` day counts as worked, past or not (work rule changed: it used to be counted as off once past); an assignment is not a shift but a type of its own (its `shiftData.shift` is `null`, the rotation's shift only remains in `baseShift`; a replaced poster holds nothing either, what they gave away is in `substitution.gave`), worked when its type is in `ASSIGNMENT_WORK_SUBTYPES` and it has hours, never for `absence` (the "Congé" of the UI), `sick_leave`, `maternity_leave` or `substitution`. `toShiftsMap` keeps only `isWorked` days, an assignment as an entry with `shift: null` and `assignment: <type>`, and the rules' `isWork` accepts either). Windows are bounded by the period like the compatibility rules (a 5/2 week is flagged on purpose). Tests: `test/workCheck.test.js`.

Day result of `computeUserShifts` (`planning.userShifts.js`, one object per day): `shiftData` is what the user **holds** that day (`shift`, `selectedVariation`, `team`) and is empty when they hold nothing (replaced, or on an assignment); `baseShift` is always the rotation's `Shift` document, what was planned (the internal `{ shift, team }` wrapper is `rotationDay`); `presence` replaces the former `isOff` boolean: `present`, `released` (a `disp` modification), `unconfirmed` (an optional rotation day nothing confirms) or `replaced` (the user gave their shift away); `isWorked` is separate (a rest day is `present` and not worked); `substitution` is `null` or describes the latest substitution entry, `{ kind: 'replaced' | 'replacing' | 'exchanged', demandId, gave: { shift, team, selectedVariation } | null }` (`replacing` took someone's shift, `exchanged` is a switch: took the other's and gave one's own); `history` lists the active assignments in order, each substitution step carrying the same object, so a chain (A replaced by B, B by C) reads step by step; `comment` is the day's note (see "Day note" below) when there is one, otherwise the comment of the day's assignment (`''` without either; each history step keeps its own assignment comment). Every substitution entry records what its user gives away in `Assignment.substitution.gave` (the poster's proposed shift; for a switch, the accepter's own), which is what makes a chain exact: B, who took J from A and passed it to C, gave J, not the shift of their own rotation (an entry created before this field falls back to the rotation's shift for a replaced user). A modification only applies to a shift the user holds: a replaced user cannot be given a shift back (`registerEntry` refuses `pres`, `disp`... and hour patches with 422), while whoever holds one (replacement accepter, either side of a switch) modifies it freely. Front: `shiftStore` keeps `presence` and `substitution`; a replaced day is drawn from `substitution.gave` (`getDisplayShiftName`, the day tile, the shift card "Remplacé", the team grid). Tests: `test/planningPresence.db.test.js` (chains and switches through the real flows on a scratch database, replica set required, skipped without MongoDB).

Day note (`models/DayComment.js`, collection `daycomments`, one document per user and day, unique index `{ userId, date }`): a free comment (max 500, `CALENDAR_COMMENT_MAX_LENGTH` in `backend/config/limits.js` and `front/src/config/limits.js`) on a day, **independent of the shift and of any entry** (assignment, modification, hour patch), on purpose not a `CalendarEntry`: no cancel, restoration to the initial shift (`deactivateEntries` / `restoreInitialShift`), assignment deletion or period cleanup (`sanitizeUserPeriod`, team change, center transfer) touches it, and it blocks nothing (a modification still works when the user holds a shift). It only goes when the user changes or deletes it. `PUT /calendar-entry/comment` (`{ date, comment }`, the token's user; `services/calendarEntry/calendarEntry.comment.js` `setDayComment`; normalised by `normalizeComment` in `utils/validation.js`, 400 above the limit; an empty comment deletes the note, and also blanks the active assignment's own comment in place so that "delete" removes what is displayed; answers the recomputed day `{ userShift, type: 'comment' }`) is declared above `hasNoPendingCenterTransfer` since it touches neither teams, points nor demands. `computeUserShifts` overlays the notes of the period (one `DayComment` query) on each day's `comment`, the note winning over an assignment's comment (`getDayCommentsByDay`). Front: the button "Ajouter / Modifier le commentaire" of `ShiftCard` (any editable day) opens `components/Dialogs/DayCommentDialog.vue` (textarea with counter, Enregistrer / Supprimer, `planningModificationService.setDayComment`, then `shiftStore.addEntry(res.userShift[0], dateKey)`); the comment keeps showing on the card under the team name. Tests: `test/dayComment.db.test.js` (service and HTTP: replace, delete, per user and day, alongside a modification, surviving an assignment, its cancellation and the restoration, assignment comment fallback, validation).

Period cleanup for a user (e.g. after a team change): `services/user/user.sanitizePeriod.js` exports `cancelUserDemandsInPeriod`, `clearUserCalendarEntriesInPeriod` and `sanitizeUserPeriod(userId, { from, to? })` (open-ended when `to` is omitted; both ends inclusive). Calendar entries are deactivated (`active: false`), never deleted, and no emails are sent.

Team ownership is stored as overlapping occurrences (`user.teams`: `{ teamId, fromDate, toDate|null }`, `toDate` inclusive; a bounded occurrence = reinforcement and beats the open-ended permanent one). `services/team/team.segments.js` turns them into contiguous segments (`buildTeamSegments`, `getOwnerTeamIdAt`) and diffs two segment lists (`diffTeamSegments` → `{ from, to, oldTeam, newTeam }`, inclusive bounds, `to: null` = unlimited, directly usable as a `sanitizeUserPeriod` period). `services/user/user.team.js` (`assignTeamToUser`, `deleteTeamOccurrence`) uses them: it first refuses (400 `TEAM_CHANGE_PAST`, `assertNoPastChange`) any change whose period starts before today in the user's center time zone (day keys compared as strings), then diffs the segments, runs `sanitizeUserPeriod` on each changed period and saves `user.teams`, all in one transaction, and returns the `changes`. Without `confirmed`, if the change would cancel demands or deactivate calendar entries, it applies nothing and returns **409** `{ needsApproval, message, segments: { before, after }, teams: { id: name }, changes: [{ from, to, oldTeam, newTeam, demands, entries }] }` (built with `previewUserPeriodImpact`, the read-only twin of `sanitizeUserPeriod`); the client re-sends with `confirmed: true` (body for `POST /user/:id/assign-team`, `?confirmed=true` for `DELETE /user/:id/team-occurrences/:occurrenceId`). `assign-team` also accepts `replaceOccurrenceId` to swap an occurrence in one atomic change. Front: `apiFetch` turns any 409 into `{ ...data, needsApproval: true }` (no throw); `components/Profile/TeamChangeImpactDialog.vue` shows the before/after timeline and the affected items. For display, `buildTeamTimeline` returns the same segments tagged `kind: 'permanent' | 'reinforcement'` (an occurrence with a `toDate` is a reinforcement), served by `services/user/user.teamTimeline.js` as `GET /user/teams/:centerId/timeline` (every team's members, past/current/future, default window 3 months before and 9 months after today) and `GET /user/:id/team-timeline` (one user's teams), both guarded by `middleware/centerAuth.js` (same center, or master). The front only draws them: `components/Teams/TeamTimeline.vue` (generic horizontal timeline: permanent = primary, reinforcement = secondary + stripes, past dimmed, today line) is used by `TeamMembersList.vue` (team members drawer, falls back to the plain list if the timeline is unavailable) and `UserTeamCard.vue`.

**Which team applies on a day is written once**, in `services/team/team.atDay.js`: `ownerAt` (a reinforcement beats the permanent team; then the latest start; on the same start day a team beats the "no team" marker), built from `reinforcementsAt` and `permanentAt`. `getTeamAtDay`, `team.segments.js` and the profile's current teams (`getUserTeamOccurrences`: permanent and reinforcement shown side by side) use it: do not write the rule again. Two questions have their own helper on purpose: "who does this user belong to in the member list" (`getUsersGroupedByTeam`: listed in the permanent team **and** in each team reinforced that day, from `permanentAt` / `reinforcementsAt`) and "who does a cycle move affect" (`holdsAnyTeamFrom` in `team.segments.js`: holds the team on or after the date, so a replaced or ended assignment does not count even without an end date). A deleted team cannot be joined (`assignTeamToUser`, sign-up: 404).

**Team occurrences are never erased** (past planning is computed from them). Losing a team (center transfer, `POST /user/:id/assign-center`, deleted center) goes through `endTeamMembership(occurrences, today)` (`services/team/team.membership.js`, `today` = the day of the center being left): past occurrences stay, running reinforcements stop the day before, anything starting today or later is removed, and a permanent **"no team" marker** `{ teamId: null, fromDate/fromDay: today, toDate: null }` is added (the schema accepts an explicit `null`, not a missing `teamId`). **Never write `user.teams = []`.** `getTeamAtDay` answers `null` for a day owned by a marker (and `buildTeamSegments` / `buildTeamTimeline` give it no segment); on the same start day a team wins over the marker. Code walking `user.teams` itself must handle `teamId: null` (see `user.teamRead.js`). The marker cannot be deleted or replaced through the team routes; a new permanent team starting before it moves it back to that day, so that removing that team leaves no team rather than the old one. A user's team history can therefore span several centers (the planning resolves each team through its own center). Test: `test/teamMembership.db.test.js`.

## Front architecture

- Scroll restoration: the experimental `ScrollRestoration` plugin of `vue-router/experimental` (installed in `plugins/index.js` **before** the router; `scrollBehavior` is deprecated and no longer set), options in `router/scrollRestoration.js`. Rule: the four bottom-navigation tabs get their saved position back, every other page opens at the top. The plugin is component-owned: it only acts for components that call `useScrollRestoration()`, and it sets `history.scrollRestoration` to `manual`, so **a page that is neither registered nor under a registered layout keeps the previous page's scroll** (the window scroll belongs to the document, not to the page). The decision by path lives in the plugin's `restore` option (tab: saved entry, otherwise `null` which the default function turns into top). Two levels of call: the layouts (general case: top) and one **root page per tab** (`pages/(tabs)/dashboard.vue`, `pages/(tabs)/planning.vue`, `pages/(tabs)/demand-page/demands.vue`, `pages/(tabs)/center.vue`), each declaring `definePage({ meta: { tab: true } })` and calling the composable once; `restore` reads `meta.tab` through `route.matched`, so a new tab is a new root page, with no list to keep in sync. The tab root's call wins over the layout's (same key, the path, the most nested wins) and restores once the page is displayed; from a layout the restore runs while the previous page is still on screen (`<transition mode="out-in">`) and is clamped to its height (measured: 1000 came back as 726). - Navigation piles per tab (`router/tabMemory.js`, reactive, in memory, emptied by `emptyAllStores` on logout): each bottom tab root page declares `definePage({ meta: { tab: '<key>' } })` (`dashboard`, `planning`, `demands`, `center`; its pages depend on it) and has its own pile of visited pages: the root page at the bottom, then the sub-pages (layout `alternative`: information, users, rotations, profile parameters...) opened from it, a sub-page without a tab of its own (information, profile) going on the pile of the tab where you are. `router.afterEach` keeps the piles (failed navigations, `failure` set, count for nothing: neither the piles nor the direct-open seeding, and the back flag is cleared there so a pop that never reached the guard cannot hijack the next navigation): a tab-level page resets its pile to itself, a sub-page is pushed, and returning to a page already on the pile (browser back or forward, or the arrow) cuts what follows. `tabTarget(key, rootPath)` is what the bottom bar and the desktop rail link to (`BottomNavigation.vue`, `DesktopNavigationDrawer2.vue`): a tab reopens at the page you left it on, and tapping the tab you are already on goes back to its root; `backTarget()` is the toolbar arrow of the `alternative` layout (pops one page; a sub-page opened directly, by address or reload, is alone on its pile, so back goes to the dashboard). - Parallax (`components/common/ParallaxLayer.vue`, no composable): wraps decorative art so that it moves a little less than the page. The layer glides by `reach` (30 by default, in % of the window height) over the **whole** scroll of the page, by a CSS animation tied to the page scroll (`animation-timeline: scroll(root block)`, run by the browser off the main thread, so no lag and no JavaScript while scrolling); so the speed depends on the page length (a long page is slower than 30 %, a very short one barely moves). Two ways (`fixed`): in the page flow (default: an element of the page placed by the caller's `class`, like the dashboard radar, pushed down by up to `reach` at the bottom of the page; its parent must be `overflow: clip` so that it never lengthens the page) or pinned to the window (`fixed`: a fixed full-window clip, under the app bar, holding a layer of constant height `100vh + reach` that slides up by `reach`, like the landing page; the art scales with that height, which therefore never changes). Browsers without scroll-driven animations (Firefox for now, Safari before 26) and reduced motion get no effect: a flow layer scrolls like the page, a pinned layer stays still. **Dialogs**: Vuetify locks the page scroll by making `<html>` `position: fixed` with a negative `top` (class `v-overlay-scroll-blocked`, scrolled distance in `--v-body-scroll-y`): the page then has no scroll for the browser and the animation would snap the art back to its start. A `MutationObserver` on `<html>` marks the layer `data-parallax-frozen` while the class is set, with the position it had (`--parallax-frozen`: scrolled / (body height - window height) × `reach`), which the stylesheet applies with the animation off; closing the dialog frees it. The pinned window also leaves `--v-scrollbar-offset` free on its right so that it does not widen when the scrollbar disappears. The layer is `aria-hidden` and takes no click. Used by `pages/(tabs)/dashboard.vue` and `pages/(public)/landing.vue`. History: an earlier version moved the layer from a JavaScript composable at exactly 30 % with a computed extra height; measured on the landing page it lagged the compositor-scrolled page (37 of 158 frames more than 1.5 px off) and its height followed the page (908 → 939 px), rescaling the art; it was replaced by this one (1 of 155 frames off, height constant).

A name built at run time (`'mdi-' + type`) is **not** seen: write the full name (`utils/entryIcons.js` stores `mdi-...`), and in dev a missing icon logs `[mdi] icône inconnue`. **Never put padding on a `v-icon`** (`pa-*`, `px-*`, a `padding` rule): `.v-icon` is `width: 1em; height: 1em` in a `border-box`, and the SVG fills its content box, so padding larger than the icon leaves a content box of zero width and the icon disappears (a font glyph used to overflow and hide the problem; measured: `px-3` on a 20 px icon gives an SVG of 0x20, `mx-3` gives 20x20): use margin (`mx-*`), or a wrapper element with the padding. - Dates: use **Temporal** (`@js-temporal/polyfill` in `backend/`, `temporal-polyfill` in `front/`: smaller, no `jsbi`, same API) for every calendar or time-zone computation (today in a center's `timeZone`, day arithmetic, comparisons, formatting between zones), in the backend and in the front. In the front always `import { Temporal } from 'temporal-polyfill'` explicitly, never use the bare global `Temporal`: recent browsers ship a native one, and mixing it with the polyfill breaks `instanceof` and Vue prop type checks ("Expected PlainDate, got Temporal.PlainDate"); the polyfill also covers Capacitor WebViews without native Temporal. Avoid new `Date` arithmetic, `setHours`, `toLocaleDateString({ timeZone })` tricks and string slicing for this; use `Temporal.Now.plainDateISO(tz)`, `PlainDate`, `ZonedDateTime`. `computeUserShifts(dayKeys, userId)` takes **day keys only**, one `YYYY-MM-DD` string or an array of them (anything else, a `Date`, an ISO string with a time, an impossible day, is a 400): it does no time-zone conversion and has no notion of "today" (the centers it reads are only those of the user's teams it needs, for the cycle anchor, once each); a caller holding an instant places it on a day first (`utils/dates/calendarDay.js` `toCalendarDay`: a plain `YYYY-MM-DD` or a UTC-midnight `Date` is a day taken as is, any other instant is placed in `Center.timeZone`; or `posterDayOf`, `eachDay`), and `getTeamAtDay` / the rotation timeline compare days, reading stored `Date`s or `YYYY-MM-DD` strings alike so the stored fields can move to strings later without touching the readers. In the backend the cycle code follows this (`utils/dates/plainDate.js`: `toPlainDate`, `toMongoDate`, `eachDay`, `daysBetween`, `compareDays`, `todayIn`; the cycle formula is in `services/team/team.cycleIndex.js`; calendar days are `Temporal.PlainDate` and a `Date` only appears at Mongo boundaries; any incoming value is read as its UTC calendar day, so a legacy `cycleStartDate` stored with a time of day loses that time). Stored days are being moved from midnight-UTC `Date` fields to `YYYY-MM-DD` strings: each old field has a string twin next to it (`activationDates` -> `activationDays`, `User.teams[].fromDate/toDate` -> `fromDay/toDay`, `personalData.birthDate` -> `birthDay`, `posterShift.date` / `accepterShift.date` -> `posterShift.day` / `accepterShift.day`, `cycleAnchorDate` -> `cycleAnchorDay`; registry and `dayField` schema type in `utils/dates/dayFields.js`). All backend writers now write both fields and all readers read the day twin first, falling back to the old `Date` field with a throttled `[jours] ...` `console.error` when the twin is missing or inconsistent (`utils/dates/dayAccess.js`: `activationDaysOf`, `posterDayOf`, `shiftDayOf`, `occurrenceDays`, `birthDayOf`, `anchorDayOf` for reads, `dayFilter` / `dayInArrayFilter` for Mongo queries, `toDay` for writes). A `[jours]` line in the logs means unmigrated data or a writer that forgot the twin: run the script below. When writing a new place that stores or reads one of these days, use those helpers. In the front, `src/utils/dayFields.js` does the same for API data (`posterDay`, `accepterDay`, `occurrenceDays`, `birthDayOf`, `activationDay`, `formatDay`, `todayKey`): it reads the day twin first, then the old ISO field, and always returns a `YYYY-MM-DD` key; compare keys (`sameDateKey`, string comparison), never `Date` objects or ISO strings, and display with `formatDay` (no browser time-zone shift). Send keys to the API too: a Vuetify date-picker value (a `Date` at local midnight) goes through `pickerDayKey` (`utils/dateKey.js`), never `toISOString()`. The old `Date` fields stay the source of truth until the twins are the only fields read. Everything that disappears at cut-over is tagged `TEMPORARY(day-fields)` in a comment (`grep -rn "TEMPORARY(day-fields)" backend front/src`): tag any new code that only exists for the migration the same way, and delete every tagged item when the old fields are dropped. `node backend/scripts/migrateDayFields.js` fills and checks the twins (dry-run by default; `--apply --confirm=<db name>` writes after saving a backup; `--check` exits 1 if anything differs; `--rollback --apply` removes the twins; values with a time of day are anomalies unless `--truncate`). A native `Date` is only for what an API forces on you (Mongoose fields, Vuetify's date picker, `toISOString` on the wire): convert at that boundary (`new Date(plainDate.year, plainDate.month - 1, plainDate.day)`), and convert existing `Date` code to Temporal when you touch it, without refactoring unrelated code. Center time zone: `Center.timeZone` (default `Europe/Paris`), served by `GET /center`.
